Application Security

Feature Testing & Recon Assessment

Timothy Dada · York University Cybersecurity Operations Capstone · 2026

This engagement is protected under a signed NDA with the client. Client name, hosts, and reproduction specifics are intentionally omitted from this public writeup. Full technical detail is available for discussion in an interview or on request.

Objective

Two related workstreams on the same platform engagement: functional feature testing of a Zero Trust connectivity product, and an external reconnaissance pass simulating what an outside party could learn with no prior access.

Tools Used

  • An internal automated testing framework (Node/Python), run locally on Windows with Docker Desktop
  • Manual UI testing across the product's admin dashboard
  • PowerShell networking utilities for connectivity and DNS checks
  • Chrome DevTools for client-side inspection

Workstream 1: Feature Testing

Validated core product functionality across policy configuration, gateway/tunnel setup, and the admin UI.

12/13
Policy types passing
4/6

4
Issues logged
  • One policy type failed to create under otherwise-valid configuration — flagged as likely unimplemented on the backend rather than a test-environment issue.
  • The core tunnel-establishment step did not complete within its expected window, which blocked the two dependent traffic tests.
  • An admin UI form had an empty required dropdown, which blocked two creation flows end-to-end — consistent with a teammate's independent finding on a related screen.
  • The test framework itself had a Windows-specific encoding bug; found and documented a working environment-variable fix.

Workstream 2: External Recon

Simulated an outside party with no credentials and no source code, working only from two public addresses, following a staged methodology (unauthenticated recon, then least-privilege authenticated testing).

  • Mapped open services and public attack surface across both target systems using standard networking tools.
  • Reviewed a public-facing web application's client-side code for leaked routes, tokens, or configuration — none found.
  • Tested the login and signup flows for common weaknesses (invalid-credential handling, injection); both held up, and signup required real phone verification, limiting self-service account creation.
  • Identified that a set of admin API routes existed and correctly rejected non-privileged requests — a positive control working as intended.
  • Identified an internal-network-reaching proxy endpoint through client-side routing logic; further access was blocked by a protocol mismatch encountered consistently across attempts.
  • Confirmed both target systems only accepted key-based access with no working key provided, consistent with the intended scope of the exercise.

Full technical detail on each item is available for discussion in an interview or on request, consistent with the NDA note above.

Outcome

Delivered a written progress report per workstream with reproduction steps and remediation notes to the client, as part of a multi-person testing team.
